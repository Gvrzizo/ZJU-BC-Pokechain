下面我就以 PokeChain 宝可梦游戏公司的实际运营架构 为背景，把两个业务——「野外捕捉的随机数流程」和「玩家之间的宝可梦交易」——分别按照 前端 → 后端 → Fabric Gateway → 链码 → 账本 的完整调用链讲清楚。

重点不是只解释每个函数做什么，而是明确：

- 前端什么时候发请求、发送什么数据、拿到什么结果。
- 后端什么时候生成数据、什么时候调用链码、什么时候返回结果。
- 链码具体检查什么、读取什么、修改什么。
- 哪些操作只是查询，哪些操作会产生链上交易。
- 操作失败时，哪一层负责处理，以及账本是否已经发生变化。

## 一、先理解整个系统的调用关系

前端 Vue

页面、玩家操作、显示结果

后端 NestJS

HTTP API、登录鉴权、业务编排、保存服务端秘密

Fabric Gateway

使用指定 Fabric 身份提交交易或查询

Fabric 链码

校验权限、业务规则，生成读写集

Fabric 账本状态

玩家、宝可梦、随机事件、交易单等记录

先明确一个很重要的区别：

前端调用后端 API，不等于调用链码；后端调用链码，也不等于链上状态已经成功提交。

例如，前端调用 `POST /api/v1/trades`，后端才会通过 Gateway 调用 `CreateTrade`。链码执行成功后，交易还要经过 Fabric 的排序和验证流程，才会成为有效的账本更新。

另外，后端可以在一次 HTTP 请求里连续调用多个链码交易，但这些交易通常不会自动构成一个跨交易的原子事务。

# 二、野外捕捉：从进入草丛到宝可梦上链

先按你们之前设计的流程来讲：

`Commit → 生成野怪 → ConsumeItem → RevealAndVerify → MintFromCapture`

这里假设玩家已经登录，后端能够识别其游戏账号，并且 `serverSeed` 由后端安全保存。

## 2.1 操作一：创建随机事件 `Commit`

目标：为一次野外遭遇创建唯一的随机事件，并提前承诺使用哪个 seed。

### 第一步：前端请求开始遭遇

玩家点击「进入草丛」。

前端调用后端：

```
POST /api/v1/encounters
Authorization: Bearer <JWT>
```

请求可以包含玩家选择的区域，例如：

```
{
  "zoneId": "forest_01"
}
```

前端不应该提交自己决定的宝可梦种类、等级或闪光结果，因为这些属于服务端需要验证的游戏规则。

### 第二步：后端生成随机事件参数

NestJS 后端负责：

1. 从 JWT 识别当前玩家。
2. 检查玩家是否可以进入该区域。
3. 生成唯一的 `eventId`。
4. 使用密码学安全随机数生成器生成 `serverSeed`。
5. 计算 `commitHash = SHA256(serverSeed)`。
6. 把 `eventId`、`serverSeed` 和必要的事件信息安全保存到 PostgreSQL。
7. 通过 Fabric Gateway 调用链码 `Commit`。

例如，后端保存的记录可以是：

| 字段           | 示例                   | 用途          |
| ------------ | -------------------- | ----------- |
| `eventId`    | `evt_1001`           | 唯一事件编号      |
| `serverSeed` | 秘密随机字节               | 之后用于验证和派生结果 |
| `commitHash` | `SHA256(serverSeed)` | 链上承诺        |
| `playerId`   | `player_17`          | 事件所属玩家      |
| `status`     | `PENDING`            | 后端业务状态      |

其中 `serverSeed` 不能以明文返回给前端。实际存储时应加密，密钥也要单独保护。

### 第三步：链码执行 `Commit`

链码大致做这些事：

```
Commit(ctx, eventId, playerId, commitHash)
    检查 eventId 尚不存在
    检查 playerId 合法
    检查 commitHash 格式合法
    写入 rand:<eventId>
        playerId
        commitHash
        status = COMMITTED
    返回成功
```

链上记录例如：

```
{
  "eventId": "evt_1001",
  "playerId": "player_17",
  "commitHash": "abc123...",
  "status": "COMMITTED"
}
```

这里的 `abc123...` 只是示意，不是真实哈希。

注意： 链码可以检查 `eventId` 不重复，但如果 `playerId` 是后端随意传入的字符串，链码仍需要验证调用者身份和玩家归属，不能只相信请求参数。

### 第四步：后端返回前端

只有确认链上 `Commit` 交易有效提交后，后端才应将遭遇视为已创建，并返回：

```
{
  "eventId": "evt_1001",
  "status": "COMMITTED"
}
```

前端拿到 `eventId` 后，可以进入遭遇页面。

如果 `Commit` 失败，后端不能假装事件已成功创建；还需要处理 PostgreSQL 中已保存的 seed，避免留下无法使用的孤立记录。

## 2.2 操作二：派生野怪种类和等级

目标：确定玩家遇到什么宝可梦，以及它的等级。

### 后端做什么？

后端根据已保存的 `serverSeed` 和事件编号，通过约定的派生算法生成结果，例如：

```
species = derive(serverSeed, eventId, "species")
level   = derive(serverSeed, eventId, "level")
```

这只是概念伪代码。真实实现应该使用明确的字节编码、随机数派生方法和映射规则，不能直接随意取哈希字符串的一部分就宣称随机分布公平。

后端再把结果保存为该事件的遭遇记录，例如：

```
{
  "eventId": "evt_1001",
  "species": "Pikachu",
  "level": 12,
  "status": "ENCOUNTERED"
}
```

然后返回前端：

```
{
  "eventId": "evt_1001",
  "pokemon": {
    "species": "Pikachu",
    "level": 12
  }
}
```

### 这一步一定需要链码吗？

不一定。

如果野怪只是临时遭遇，还没有产生需要上链的资产，可以由后端派生并展示。

但这里有一个安全问题：后端知道 `serverSeed`，因此它也能提前预测结果。链上的承诺不会自动阻止后端把不喜欢的遭遇丢弃。

如果正式运营要求链上可验证，就应该将遭遇参数和派生规则绑定到事件，并在后续的链码交易中验证这些参数。否则，这一步只是服务端给前端的一个结果，前端不能仅凭结果相信公司没有操纵它。

## 2.3 操作三：投球并扣除精灵球 `ConsumeItem`

目标：玩家投出一个球后，扣除相应道具。

### 第一步：前端发送投球请求

玩家点击「投球」，前端调用：

```
POST /api/v1/encounters/evt_1001/throw
```

请求示例：

```
{
  "itemId": "poke_ball"
}
```

前端不应该自行发送「我有 100 个球」或「捕捉成功」这样的可信结果。库存数量和最终捕捉结果由后端协调、链码验证。

### 第二步：后端调用链码

后端从登录身份中识别玩家，再通过 Gateway 调用：

```
ConsumeItem(ctx, playerId, "poke_ball", 1, eventId)
```

### 第三步：链码检查和修改账本

链码应检查：

1. 当前调用者是否有权操作这个玩家的库存。
2. `eventId` 是否属于该玩家。
3. 随机事件是否处于允许投球的状态。
4. 玩家是否拥有足够的精灵球。
5. 该次投球是否重复提交。

通过后，在账本中扣减道具数量。

例如：

```
投球前：poke_ball = 5
投球后：poke_ball = 4
```

如果库存不存在或数量不足，链码返回错误，本次交易不会有效扣除道具。

### 这里有个需要你们明确的设计问题

如果 `ConsumeItem` 和后面的捕捉操作是两笔独立的 Fabric 交易，那么扣球成功后，即使捕捉交易失败，精灵球也不会自动返还。

这可能正是游戏想要的规则：投球就消耗球，不论是否捕获成功。但如果你们希望失败时返还道具，就必须明确补偿机制，而不是认为 Fabric 会跨交易自动回滚。

## 2.4 操作四：首次投球前 `RevealAndVerify`

目标：公开之前承诺的 `serverSeed`，验证它没有被提交后替换。

### 前端

前端不需要自己生成或猜测 `serverSeed`。它可以请求后端：

```
POST /api/v1/random/evt_1001/reveal
```

### 后端

后端读取自己保存的 `serverSeed`，然后通过 Gateway 提交：

```
RevealAndVerify(ctx, eventId, serverSeed)
```

### 链码

链码读取 `rand:evt_1001`，检查：

- 事件存在。
- 当前状态允许 Reveal。
- 当前调用者有权揭示这个事件。
- `SHA256(serverSeed)` 与链上的 `commitHash` 一致。

验证成功后，将状态更新为：

```
COMMITTED → REVEALED
```

后端在确认该交易有效提交后，才告诉前端 Reveal 成功。

### 为什么是首次投球前？

因为这让游戏公司在捕捉结果产生之前就公开 seed，玩家可以检查承诺是否一致，并依据公开算法复算对应的随机值。

但要记住：Reveal 只能证明 seed 与之前的承诺一致，不能证明公司在 Commit 之前没有试过其他 seed。 而且，如果投球已经先扣球、Reveal 才失败，扣球不会自动回滚；因此，正式实现最好先明确随机事件的状态机和调用顺序，避免扣球后卡在无法继续的状态。

## 2.5 操作五：捕捉成功并铸造宝可梦 `MintFromCapture`

目标：捕捉成功后，将新的宝可梦作为链上资产写入账本。

### 前端

前端展示投球动画。动画结束后，请求后端处理捕捉结果：

```
POST /api/v1/encounters/evt_1001/capture
```

但动画结束并不等于捕捉成功。前端不能通过请求参数决定宝可梦一定被捕获。

### 后端

后端读取该事件的 seed、遭遇参数和投球记录，按照固定规则计算捕捉结果，再提交链码交易。

例如，概念上：

```
captureResult = derive(
    serverSeed,
    eventId,
    "capture"
)
```

如果成功，后端调用 `MintFromCapture`。如果失败，则根据游戏规则记录捕捉失败，不铸造宝可梦。

### 链码

链码至少需要验证：

1. 随机事件存在，且属于当前玩家。
2. 事件已满足 Reveal 和捕捉条件。
3. 遭遇参数与该事件绑定，不能随意更换宝可梦种类或等级。
4. 随机事件尚未被消费。
5. 捕捉成功条件符合公开的派生规则。
6. 新的宝可梦 ID 尚未使用。

全部通过后，在同一笔链码交易里：

```
写入 pokemon:<pokemonId>
    owner = playerId
    species = Pikachu
    level = 12
    ...

更新 rand:<eventId>
    status = CONSUMED
```

这两个写入属于同一笔链码交易。只要该交易没有有效提交，就不会出现「宝可梦已经铸造，但随机事件没有消费」这样的部分链上结果。

不过，如果链码只是接受后端传来的 `captureResult=true`，却没有独立验证结果，后端仍然可以撒谎。 正式运营时必须明确哪些结果由链码重算，哪些由可信的外部随机服务提供，以及如何验证外部输入。

# 三、宝可梦交易：从创建交易单到双方交换完成

接下来讲你给出的四个操作：

1. `CreateTrade`
2. `ConfirmTrade`
3. `CancelTrade`
4. `ExpireTrade`

这里假设甲和乙要交换宝可梦，同时乙需要向甲支付 200 积分。

为了方便理解，假设链上初始状态是：

| 资产    | 所有者 | 状态     |
| ----- | --- | ------ |
| 宝可梦 A | 甲   | `IDLE` |
| 宝可梦 B | 乙   | `IDLE` |
| 甲的积分  | 甲   | 100    |
| 乙的积分  | 乙   | 500    |

交易规则：A、B 互换，乙额外向甲支付 200 积分。

## 3.1 操作一：`CreateTrade` 创建交易单

### 前端做什么？

甲在交易页面选择自己的宝可梦 A、乙的宝可梦 B，以及积分补差，点击「发起交易」。

前端请求后端：

```
POST /api/v1/trades
```

请求示例：

```
{
  "counterpartyId": "player_B",
  "pokemonOffered": "pokemon_A",
  "pokemonRequested": "pokemon_B",
  "pointsFromCounterparty": 200
}
```

这些参数只是甲提出的交易条件，不代表它们已经被认可。

### 后端做什么？

NestJS 后端负责：

1. 从登录 JWT 中识别发起人甲。
2. 校验请求格式和交易参数。
3. 生成唯一交易单 ID，例如 `trade_1001`。
4. 通过 Fabric Gateway 调用 `CreateTrade`。
5. 等待交易被确认有效提交，再返回结果给前端。

后端不应该只因为甲在请求中写了 `pokemon_A` 就认为它属于甲。最终的资产归属必须由链码从账本中验证。

### 链码做什么？

`CreateTrade` 从账本读取：

- `pokemon:pokemon_A`
- `pokemon:pokemon_B`
- 双方玩家记录及积分记录（如果交易规则需要）。

然后执行检查：

```
A 的 owner == 甲
B 的 owner == 乙
A.status == IDLE
B.status == IDLE
甲 != 乙
积分条件合法
交易 ID 不存在
```

全部通过后，链码在同一笔交易中执行：

```
pokemon_A.status = LOCKED_TRADE
pokemon_A.lockRef = trade_1001

pokemon_B.status = LOCKED_TRADE
pokemon_B.lockRef = trade_1001

写入 trade:trade_1001
    from = 甲
    to = 乙
    status = PENDING
    confirmations.from = false
    confirmations.to = false
    pointsFromCounterparty = 200
```

这里的 `lockRef` 非常重要：它记录这只宝可梦被哪一笔交易锁定，防止其他交易单重复使用它。

### 返回前端

```
{
  "tradeId": "trade_1001",
  "status": "PENDING"
}
```

前端显示「等待双方确认」。

注意： 这时并没有交换所有权，也没有划转积分。只是锁定资产，创建交易单。

## 3.2 操作二：甲调用 `ConfirmTrade`

甲打开交易单，点击「确认交易」。

### 前端

```
POST /api/v1/trades/trade_1001/confirm
```

### 后端

后端从登录身份识别甲，调用：

```
ConfirmTrade(ctx, "trade_1001")
```

不应该让前端通过传入 `"playerId": "player_B"` 来冒充乙。

### 链码

链码读取 `trade:trade_1001`，验证：

- 交易单存在。
- 当前交易尚未取消、过期或执行。
- 调用者是交易参与方之一。
- 对应的资产仍然被这笔交易锁定。

然后记录甲的确认：

```
confirmations.from = true
```

因为乙尚未确认，所以交易仍然处于 `PENDING`。

此时：

- A 仍属于甲。
- B 仍属于乙。
- 乙尚未支付积分。
- 两只宝可梦仍然被锁定。

前端得到成功响应后，显示「你已确认，等待对方确认」。

这里的确认操作本身也是一笔 Fabric 交易。确认状态写入账本，其他客户端查询时也能看到。

## 3.3 操作三：乙调用 `ConfirmTrade`，完成交换

这是整个流程最关键的一步。

乙在自己的交易页面点击「确认交易」。

前端发送请求，后端使用乙的 Fabric 身份调用同一个合约函数：

```
ConfirmTrade(ctx, "trade_1001")
```

链码读取交易单，发现：

```
甲已经确认
乙现在确认
交易仍为 PENDING
```

于是链码不只是记录乙的确认，而是继续执行最终结算。

### 链码在同一笔交易中完成什么？

1\. 再次验证资产锁定

确认 A、B 的 `lockRef` 都是 `trade_1001`，状态仍为 `LOCKED_TRADE`。

2\. 交换所有权

`pokemon_A.owner = 乙`

`pokemon_B.owner = 甲`

3\. 划转积分

乙的积分减 200，甲的积分加 200。链码还要验证乙余额足够，避免扣成负数。

4\. 解锁资产

两只宝可梦恢复为 `IDLE`，并清除 `lockRef`。

5\. 更新交易单

`confirmations.to = true`，`status = EXECUTED`。

这些修改全部属于同一笔 `ConfirmTrade` 链码交易。

如果余额不足、资产锁定不匹配，或者其他业务条件失败，链码应抛出错误，整笔交易不会有效提交。

这里有一个 Fabric 特有的细节：链码模拟执行时产生读写集，Peer 在提交阶段还会检查读集版本。如果模拟后相关账本数据被其他有效交易修改，这笔交易也可能因为 MVCC 冲突而无效。

### 前端最后看到什么？

后端确认交易有效提交后，返回：

```
{
  "tradeId": "trade_1001",
  "status": "EXECUTED"
}
```

前端刷新交易单、双方宝可梦信息和积分余额，显示「交易成功」。

如果后端只是收到了链码的模拟执行成功结果，却没有确认最终提交状态，就不能直接告诉玩家交易已完成。实际实现应区分交易提交成功、交易被判无效，以及提交状态暂时未知等情况。

## 3.4 操作四：`CancelTrade` 取消交易

假设甲已经确认，但乙不想交易了。

前端点击「取消交易」，调用：

```
POST /api/v1/trades/trade_1001/cancel
```

后端使用甲的身份调用：

```
CancelTrade(ctx, "trade_1001")
```

链码检查：

- 交易单存在。
- 交易尚未执行。
- 当前状态允许取消。
- 调用者符合取消权限规则。

通过后，链码在同一笔交易中：

```
pokemon_A.status = IDLE
pokemon_A.lockRef = ""

pokemon_B.status = IDLE
pokemon_B.lockRef = ""

trade.status = CANCELLED
```

积分没有划转，所有权也没有改变。

前端刷新后显示「交易已取消」，两只宝可梦重新可以参与其他活动。

一个重要的竞态问题： 如果甲取消和乙确认同时发生，两笔交易可能争用同一交易单。Fabric 的状态版本检查和链码状态校验必须确保不会同时得到「成功取消」和「成功执行」两种有效结果。

## 3.5 操作五：`ExpireTrade` 过期交易

假设交易单规定 24 小时内必须完成确认，超时后自动失效。

这里的「自动」不是指账本里的时间到了就会自行运行链码。通常需要后端定时任务检查过期交易，并发起 `ExpireTrade` 交易。

### 后端定时任务

NestJS 后端定期查询待处理交易，找出超过截止时间的交易单，然后调用：

```
ExpireTrade(ctx, "trade_1001")
```

也可以由玩家打开交易页面时触发检查，或者通过其他受控的调度服务发起。

### 链码

链码不能盲信后端说「它过期了」。它需要根据链上保存的截止时间和可信的时间规则进行验证。

检查通过后：

```
trade.status = EXPIRED

pokemon_A.status = IDLE
pokemon_A.lockRef = ""

pokemon_B.status = IDLE
pokemon_B.lockRef = ""
```

不会交换宝可梦，也不会划转积分。

这里需要注意，Fabric 的链码执行时间不应该被直接当作可靠的业务时间来源。你们应当明确截止时间如何确定、如何验证，以及所使用的时间来源是否符合公平性要求。

# 四、把前后端与链码的职责放在一张表里

| ----------------- | ----------- | --------------------- | -------------- |
| `Commit`          | 发起遭遇、显示状态   | 生成 seed、算哈希、保存秘密、提交交易 | 验证并记录承诺        |
| 派生野怪              | 展示种类和等级     | 按固定算法派生结果             | 必要时验证结果与事件绑定   |
| `ConsumeItem`     | 发送投球请求      | 识别玩家、调用 Gateway       | 检查库存、扣除道具、防止重复 |

| `CreateTrade`     | 选择资产、发起交易   | 识别甲、生成交易单 ID、提交交易     | 验证归属、锁定资产、写交易单 |
| 甲 `ConfirmTrade`  | 确认交易        | 使用甲的身份提交交易            | 记录甲的确认         |

## 五、最后用一句话区分三层

- 前端 Vue： 玩家点击什么、看到什么。
- 后端 NestJS： 收到请求后应该按什么顺序做事，调用哪些服务，以及如何处理失败。
- 链码合约： 哪些操作在业务规则下被允许，以及最终哪些数据可以写进 Fabric 账本。

最关键的设计原则是：前端负责交互，后端负责协调，链码负责强制执行不可绕过的业务规则。

后端可以帮玩家组织交易，但不能凭自己一句「交易成功」就改变宝可梦所有权；必须由链码验证交易条件，并由 Fabric 将有效交易提交到账本。
