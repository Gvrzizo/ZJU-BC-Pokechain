## P2 为什么做这个系统（30 秒）

- 版式：五条竖排，每条「一句结论 + 一行证据」
- 屏上文字：
  - 资产归属不该由运营方单方面决定 → 宝可梦/道具/积分上链，双组织背书
  - 抽卡与暴击需要可复核 → 承诺-揭示，任何人可重算
  - 押注争议需要中立裁判 → 第二组织仲裁，运营方签不出
  - 交换必须原子 → 双方确认在同一笔交易内完成
  - 游戏是验证许可链边界的好场景 → 什么该上链、什么不该
- 图：左侧五条列表，右侧一个"普通数据库 ❌ / 联盟链 ✅"的小对照
- 逐字稿：
  - 我们不是为做游戏而做游戏。第一，资产归属如果只存在运营方的数据库里，玩家只能相信我们，链上 ownerId 加上双组织背书后，单方改不了。
  - 第二，抽卡和暴击是最容易被怀疑作弊的地方，我们用承诺-揭示让任何人可以按公式重算。
  - 第三，押注对战必然有争议，所以仲裁权必须给第二个组织，运营方即使控制后端也签不出那个签名。
  - 第四，交易要么全成要么全不成，不能出现宠物给了、积分没到。
  - 最后，游戏天然有高频操作，正好用来回答"哪些必须上链、哪些必须留在链下"这个问题。

## P5 后端技术栈（35 秒）

- 版式：左侧五组「技术 → 用途」，右侧一条请求链路
- 屏上文字：
  - NestJS 10：模块化后端，12 个业务域
  - TypeORM + PostgreSQL：账号、日志、审计
  - Redis：会话、限流、房间、临时状态
  - Socket.IO：对战房间的实时推送
  - fabric-gateway + fabric-ca-client：发交易、发证书
- 图：右侧竖排 `守卫 → 拦截器 → 控制器 → 服务 → ChainAdapter → Gateway`
- 逐字稿：
  - Nest 的核心价值是横切逻辑集中：守卫管 JWT 和角色，拦截器管防重放，管道管参数校验，一个入口全部处理。
  - 持久数据用 TypeORM 加 PostgreSQL；临时数据用 Redis，比如限流计数、对战房间、捕捉会话。
  - 链上交互全在最后一层 ChainAdapter：真链走 fabric-gateway，演示模式走内存 Mock。业务代码不关心是哪种。

## P6 系统架构（45 秒）

- 版式：五层堆叠 + 右侧一次写请求的路径
- 屏上文字：
  - 表现层：浏览器，不直连区块链
  - 应用层：NestJS，负责编排与鉴权
  - 接入层：Fabric Gateway，用证书签名
  - 区块链层：2 peer + 1 orderer + 2 CouchDB
  - 支撑层：PostgreSQL / Redis / MinIO
- 图：
  - 左：五层框，应用层与区块链层之间单独画一格 `Gateway`
  - 右：`浏览器 → nginx → NestJS → Gateway → peer×2 背书 → orderer 排序 → 写入账本`
- 逐字稿：
  - 一次写操作要经过：nginx 反代、后端鉴权、业务编排、Gateway 用证书签名、两个 peer 各自执行并背书、orderer 排序出块、最后才写进账本。
  - 中间任何一步失败，账本都不会变。读操作不需要背书，只走 evaluate。

## P7 链上存什么，八个合约（45 秒）

- 版式：左表右合约网格
- 屏上文字：
  - 链上七类数据：玩家、宝可梦、道具、交易单、对战单、随机事件、幂等记录
  - 不上链：战斗计算、地图、日志、图片
  - 八合约：账户、随机、宝可梦、道具、交易、对战、履历、繁殖
  - 资产状态机：空闲 / 交易锁 / 对战锁
  - 每笔变更交易带幂等键，重放返回首次结果
- 图：左七行小表；右八张合约卡片（履历、繁殖用强调色）；底部一行 `IDLE ⇄ LOCKED_TRADE / LOCKED_BATTLE`
- 逐字稿：
  - 判断标准只有一条：会不会易主、有没有争议。会，就上链；不会，就留在链下。
  - 所以 HP、能力值、战斗日志、房间、图片都不在链上。
  - 资产有三个状态，锁定期间不能转移、不能消耗、不能被第二笔交易再锁，双花在状态机层面被挡住。
  - 幂等键保证重试安全：同一个键第二次提交直接返回第一次的结果。

## P8 双组织、背书与身份（40 秒）

- 版式：左右两栏
- 屏上文字：
  - 背书策略 MAJORITY，两组织等于双方都要签
  - 链码升级也要双方批准，单方改不了规则
  - 角色写在证书属性里，链码读证书判权限
  - 仲裁角色强制属于 Org2
  - 争议时资产冻结，只有 Org2 能出终局
- 图：左栏 `交易 → peer0.org1 → peer0.org2 → 两个签名`；右栏 `CA → 证书(role) → 链码校验`
- 逐字稿：
  - 双组织不是为了好看。背书策略是两方都要签，所以运营方单方面改不了账本，也改不了链码。
  - 玩家的角色写在证书里，链码用 `hf.EnrollmentID` 认人、用 `role` 认权限，后端伪造不了。
  - 仲裁员必须是 Org2 的证书，这一条让裁判真的独立于运营方。

## P9 可验证随机数（35 秒）

- 版式：三步状态机 + 公式 + 局限
- 屏上文字：
  - 链码不能随机：两个 peer 执行结果必须一致
  - 种子在链下生成，链上只存哈希
  - 用时上链重算校验，一个事件只能消费一次
  - rand(n)=HMAC-SHA256(seed, client|event|n)
  - 局限：后端在揭示前能看到种子
- 图：`COMMITTED → REVEALED → CONSUMED` 三格；下方公式；右下角小字"任何人可复算"
- 逐字稿：
  - Fabric 是先执行后排序，同一笔交易两个 peer 各跑一遍，结果必须一样，所以链码里不能有随机数和系统时间。
  - 我们把随机放到链下，但承诺先上链：先存 sha256(种子)，用时再揭示，链上重算一遍。
  - 派生用 HMAC，把玩家种子、事件 id、序号绑在一起，可以按索引取任意一个值。
  - 最后一条局限我们主动写进文档：运营方理论上能提前看到种子，升级方案是外部随机信标或 VRF。

## P10 两处链上扩展：履历与血统（30 秒）

- 版式：左右分栏
- 屏上文字：
  - 履历：账本自带历史，初训家与转手次数不可篡改
  - 履历：时间线由相邻版本比对，旧记录也查得到
  - 血统：子代记录双亲与代数，血统哈希由链码计算
  - 血统：IV/性格/闪光由链码按随机流重算，后端改不了
  - 两处都是独立合约，可整块卸载
- 图：左时间线（收服 → 改名 → 易主）；右双亲箭头指向子代，旁边标 `HEREDITY_MISMATCH`
- 逐字稿：
  - 履历是只读查询，直接从账本历史取，不新增任何写路径；初训家和转手次数按完整历史统计，所以截断不会算错。
  - 血统繁殖复用现有随机事件，链码自己按种子把 IV、性格、闪光重算一遍再比对，后端填个 31 会直接被拒。

## C1 组件速查（每个部件是什么、在本项目干什么）

### 前端

| 组件 | 是什么 | 在本项目负责 |
|---|---|---|
| Vue 3 | 渐进式前端框架 | 页面、组件、路由切换 |
| TypeScript | JS 的类型超集 | 全仓库类型约束，接口字段漂移能被测试抓到 |
| Vite | 构建工具 | 开发热更新、生产打包 |
| Pinia | Vue 的状态管理 | 登录态、队伍、背包、区域等共享状态 |
| Vue Router | 路由 | `/game`、`/team`、`/breeding` 等页面 |
| Phaser 3 | 2D 游戏引擎（Canvas/WebGL） | 地图行走、碰撞、战斗动画 |
| axios | HTTP 客户端 | 调 REST，拦截器统一加 JWT 与防重放头 |
| socket.io-client | WebSocket 客户端 | 对战回合、房间状态实时推送 |
| Web Crypto | 浏览器密码学 API | 素材 sha256 校验、公平性页面复算 HMAC |
| nginx | 静态服务器 + 反向代理 | 托管前端产物，把 `/api`、`/socket.io` 转给后端 |

### 后端

| 组件 | 是什么 | 在本项目负责 |
|---|---|---|
| NestJS | Node 的服务端框架（模块/控制器/服务） | 12 个业务域、依赖注入 |
| 守卫（Guard） | 请求进入前的拦截点 | JWT 校验、角色校验（admin/arbitrator） |
| 拦截器（Interceptor） | 请求前后处理 | `X-Nonce`/`X-Timestamp` 防重放 |
| 管道（Pipe） | 参数校验与转换 | class-validator 白名单，剥掉多余字段 |
| TypeORM | ORM | 用户、战斗日志、审计、改名计数等表 |
| PostgreSQL | 关系型数据库 | 持久业务数据（账号、加密证书、日志） |
| ioredis | Redis 客户端 | 会话、限流、房间、捕捉会话、排行榜 |
| Socket.IO | WebSocket 服务端 | `/battle` 命名空间，服务端权威推送 |
| argon2 | 口令哈希算法 | 注册与登录 |
| JWT | 令牌 | access 15 分钟 / refresh 7 天，Redis 白名单 |
| MinIO SDK | S3 兼容对象存储客户端 | 素材上传与预签名 URL |
| fabric-gateway | Fabric 官方 2.5 客户端 | 提交交易（submit）/ 查询（evaluate） |
| fabric-ca-client | Fabric CA 客户端 | 注册与 enroll 玩家证书 |
| ChainAdapter | 自建抽象层 | 真链 / Mock 两套实现，业务无感 |

### 区块链层

| 组件 | 是什么 | 在本项目负责 |
|---|---|---|
| Peer | 记账与背书节点 | 执行链码、算读写集、签名、写账本 |
| Orderer | 排序服务（单节点 Raft） | 收交易、排顺序、打包成块（2 秒） |
| Fabric CA | 证书颁发机构 | 给玩家与 system 签 X.509，角色写入证书 |
| MSP | 成员服务提供者 | 定义"谁属于哪个组织"，验证签名链 |
| 通道（Channel） | 账本的逻辑隔离 | 本项目一个通道 `gamechannel` |
| 链码（Chaincode） | 跑在 peer 侧的业务代码 | 8 个合约，TypeScript 编写 |
| 世界状态 | 当前值（CouchDB） | 按 key 存玩家、宝可梦、交易单等 |
| 账本 | 不可变的区块日志 | 历史查询、审计、争议取证 |
| 背书策略 | 交易需要哪些组织签名 | MAJORITY = 两组织都要签 |

### 基础设施

| 组件 | 是什么 | 在本项目负责 |
|---|---|---|
| Docker Compose | 容器编排 | 应用层 5 个服务、Fabric 网络 7 个容器 |
| Redis | 内存 KV | 见上；也是 Mock 链的状态存储（`mockchain:*`） |
| MinIO | 自建对象存储 | 图片音频，链上只存 `uri + metadataHash` |
| admin CLI | peer 命令行 | 部署链码、查通道、查历史 |

## C2 一次野外捕捉：五层职责（逐操作）

> 实际流程：`Commit → 派生野怪 → （野怪战斗/投球）ConsumeItem → 结算后 RevealAndVerify → MintFromCapture`
> **注意**：本仓库是"结算后揭示"（H9），不是"首次投球前揭示"；失败投球保持 COMMITTED，`/fairness` 对 COMMITTED 裁剪种子。

| 操作 | 前端 | 后端 | Gateway | 链码 | 账本 |
|---|---|---|---|---|---|
| `POST /capture/encounter` → `Commit` | 点"进入草丛"，传区域/诱饵 | 生成 `serverSeed`、算 `commitHash`、存 Redis 会话 | 用 players 证书 submit | 校验 eventId 唯一、hash 格式，写 `rand:*` = COMMITTED | 新增一条随机事件 |
| 派生野怪（链下） | 展示种类/等级预览 | 按 `rand(0)/rand(1)` 从区域池加权抽样 | — | **不参与** | 不变 |
| 野怪战斗 / `POST /wild/:id/action` | 出招、投球、逃跑 | 读会话、算回合、投球判定（`rand` 30000/attempt 区） | 扣球时 submit `ConsumeItem` | 校验归属与 IDLE，扣数量，写 `item:*` | 道具数量变化 |
| 结算 `RevealAndVerify` | 展示"已验证" | 从 Redis 取明文种子提交 | system 证书 submit | 重算 `sha256(seed)==commitHash`，不匹配抛 `SEED_MISMATCH` | 随机事件 → REVEALED |
| `MintFromCapture` | 展示新宝可梦 | 组装个体（IV/性格/闪光/技能）、算 dnaHash | system 证书 submit | `consumeRandom` 校验 purpose/playerId/状态，写 `pokemon:*` | 新增资产 + 随机事件 → CONSUMED |

失败归属：

| 失败点 | 谁处理 | 账本是否已变 |
|---|---|---|
| 前端参数不合法 | 前端 + 后端管道 | 否 |
| 余额/道具不足 | 链码抛错 | 否（整笔回滚） |
| 种子对不上 | 链码 `SEED_MISMATCH` | 否 |
| 后端在 Commit 后崩溃 | 会话 TTL 过期，随机事件停在 COMMITTED（留痕） | 是（承诺已上链，这是设计意图） |

## C3 一次交易：五层职责（逐操作）

| 操作 | 前端 | 后端 | Gateway | 链码 | 账本 |
|---|---|---|---|---|---|
| `POST /trades` | 选自己的 offer、对方的 request | 校验归属、组装、生成 tradeId | 用发起人证书 submit `CreateTrade` | 逐项校验归属与 IDLE，锁成 `LOCKED_TRADE(lockRef=tradeId)`，算 `manifestHash` | 交易单 + 资产锁定 |
| 甲 `POST /trades/:id/confirm` | 点确认 | 用甲证书提交 | submit `ConfirmTrade` | `confirmations.from=true` | 确认位更新 |
| 乙 `POST /trades/:id/confirm` | 点确认 | 用乙证书提交 | submit `ConfirmTrade` | 双确认后**同一笔交易内**：换 owner → 划积分 → 解锁 → EXECUTED；宝可梦 bond 重置 30 | 归属与积分同时变化 |
| `POST /trades/:id/cancel` | 点取消 | 校验是当事人 | submit `CancelTrade` | 仅 OPEN 可取消；解锁全部资产 | 资产回 IDLE |
| 过期（惰性触发） | 列表显示已过期 | 查询时发现过期则触发 | submit `ExpireTrade` | `nowISO >= expiresAt` 才允许；解锁 | 交易单 EXPIRED |

为什么要两次确认：**单方确认就能换资产等于可以偷**。第二次确认发生在同一笔链码交易里，所以不会出现"宠物过户了、积分没到"。

## C4 一次繁殖：五层职责

| 步骤 | 前端 | 后端 | Gateway | 链码 | 账本 |
|---|---|---|---|---|---|
| 选亲代 | 培育屋列出可选亲代（等级/状态过滤） | 预校验同 owner、IDLE、等级 | — | — | 不变 |
| `Commit` | — | 生成种子，`purpose='mint'` | 玩家证书 submit | 写 `rand:*` COMMITTED | 新增随机事件 |
| `RevealAndVerify` | — | 提交明文种子 | system 证书 submit | 重算哈希 | REVEALED |
| 派生 | — | 按 50000 区算 IV/性格/闪光 | — | **不参与** | 不变 |
| `Breed` | 显示子代卡片 | 提交子代字段 | 玩家证书 submit | 校验双亲、`consumeRandom`、**重算属性比对**（不符 `HEREDITY_MISMATCH`）、扣 200P、写 `pokemon:*` | 子代 + 积分减少 |

## C5 三层职责一句话

| 层 | 负责 | 不负责 |
|---|---|---|
| 前端 Vue | 玩家点什么、看到什么 | 不做判定，不做信任假设 |
| 后端 NestJS | 按什么顺序做事、失败怎么处理、秘密怎么保管 | 不能凭自己说"成功"就改归属 |
| 链码 | 什么被允许、什么能写进账本 | 不做高频计算、不产生随机数 |

**核心原则：前端负责交互，后端负责协调，链码负责强制执行不可绕过的规则。**

## C6 常见追问（技术向）

| 问题 | 回答 |
|---|---|
| 前端调后端 = 上链了吗 | 不等于。只有后端通过 Gateway 提交且 peer 背书、orderer 出块、验证通过，才算写进账本 |
| 一次 HTTP 请求能包含多笔链码交易吗 | 能（捕捉是 3–5 笔），但它们**不是**跨交易原子事务，失败时要靠幂等键和状态机补偿 |
| 读操作要背书吗 | 不要。`evaluate` 走单 peer，不产生区块 |
| 为什么不用区块哈希当随机源 | Fabric 交易在执行阶段拿不到区块信息；链码也不允许依赖不确定性 |
| 链上时间可信吗 | 区块时间只作展示；业务时间用入参 `nowISO`，这是已知取舍，生产应由可信时钟或预言机提供 |
| Mock 模式算不算造假 | Mock 复刻链码语义并跑同一套测试与对拍向量，真链也实际部署验证过 |
| 数据量多大 | 8 个合约、5 张 CouchDB 索引、15 张地图、386 个种族 |

## C7 与 `docs/gpt_answer.md` 的差异（以代码为准）

| 该解析的写法 | 本仓库实际 |
|---|---|
| `POST /api/v1/encounters` | `POST /api/v1/capture/encounter` |
| 首次投球前揭示 | 结算后揭示（快速捕捉投中时 / 野怪战斗终态），失败投球保持 COMMITTED |
| 交易过期靠定时任务 | 列表查询时惰性触发 `ExpireTrade`，链上不跑定时器 |
| 后端可自由选择身份 | 玩家交易用玩家证书（`hf.EnrollmentID` 认人），system 身份仅用于编排类交易 |
| 只讲捕捉与交易 | 另有对战、繁殖、履历三条链路，结构同构（本文 C2–C4） |
