# PokeChain 项目评审报告

> 评审日期：2026-10-25  
> 评审对象：`Pokechain` 仓库（链码 `chaincode/pokemon-cc`、后端 `backend`、前端 `frontend`、Fabric 网络 `network`）  
> 评审方式：全量静态阅读 + 三套单测 + Mock 端到端 + 真实 Fabric 端到端 + 链上账本查询 + 链码越权实证  
> 结论一句话：**代码不是“假区块链”，Fabric 链路、背书、账本、事件都是真的；但“真链开箱即用”是断的，且链码把身份/铸造/养成的最终裁判权留给了后端，导致区块链目前主要是一个可信资产台账，而不是公平裁判。**

### 2.1.2 最严重的三个问题（展开）

#### C1：链码身份校验退化为“是不是 Org1”

`assertCallerIsPlayer` 的实现是：

```ts
export function assertCallerIsPlayer(ctx: Context, player: Player): void {
  const caller = getMspId(ctx);
  if (caller !== player.mspId) {
    fail('NOT_OWNER', `caller msp ${caller} does not match player ...`);
  }
}
```

所有普通玩家都在 `Org1MSP`，所以这个检查对任意玩家都成立。它保护的是“别的组织不能动”，不是“别的玩家不能动”。受影响交易至少包括：

- `TransferPoints`（可直接转走他人积分）；
- `ConfirmTrade` / `CancelTrade`（可替对方确认/取消）；
- `ConfirmResult` / `Dispute`（可替对方确认结果/发起争议）；
- `CreateBattle`（任意 Org1 身份可替双方建房并锁资产）；
- `RegisterPlayer`（可抢注任意 playerId）；
- `ApplyGrowth` / `Transfer` / `Release` / `MergeStacks` / `ConsumeItem`（可改/转/放生/消耗他人资产）。

我们在真实 Fabric 上用**一个普通玩家证书**（后端托管的 `auditattacker`）直接调用链码，成功完成：

```text
OK TransferPoints from victim: {"fromId":"auditvictim","toId":"auditattacker","amount":10,
  "fromBalance":990,"toBalance":1010}
```

这不是“后端 API 越权”，而是**链码第二道防线失效**。正常 Web 流程下用户拿不到私钥（后端托管），所以需要“后端/DB+密钥失陷”或“用户拿到自己的证书”才能利用；但课程文档明确把“链码 CID 再校验一次”作为独立防线（`docs/security.md` §1.2），这道防线目前不存在。

**修复（建议直接做）**：

- `Player` 增加 `enrollmentId`（注册时取 `ctx.clientIdentity.getAttributeValue('hf.EnrollmentID')`），`assertCallerIsPlayer` 改为比较 enrollmentId；
- 或在链码里直接读 `getAttributeValue('hf.EnrollmentID')` 与 `player.playerId` 比较（本项目 playerId 就是用户名）；
- 给 `TransferPoints` / `ConfirmTrade` / `ConfirmResult` / `ApplyGrowth` 增加“非本人/非 system 拒绝”的链码测试；
- 注意：`hf.EnrollmentID` 是 Fabric CA 的固定属性，证书里会自动带，**不要**再显式注册（见 C4a）。

#### C2/C3：链码不校验“谁可以铸造/养成”，游戏规则仍由后端说了算

`MintFromCapture` 只做了：

```ts
await loadPlayer(ctx, playerId);
await consumeRandom(ctx, eventId, 'capture', playerId);
```

没有 `requireRole('system')`。`RevealAndVerify` 同样没有角色校验。`ApplyGrowth` 对 owner 开放全部字段：

```ts
level?, exp?, moves?, evs?, ivs?, speciesId?, name?
```

只校验 EV 总量/单项、IV 范围、等级单调，**不校验成本、不校验学习表、不校验进化条件**。

实测（同一普通玩家证书）：

```text
OK MintFromCapture: speciesId 150, shiny true, ivs 全 31, moves 4 个
OK ApplyGrowth: level 100, exp 1000000, evs hp/atk 255, speciesId 151, name "Mew"
```

后果：

- 任何拿到自己证书的玩家可以免费获得 6V 闪光神兽，绕过捕捉、稀有度、传说限制；
- 任何 owner 可以把宝可梦直接改到 100 级/满 EV/任意 species，绕过训练、糖果、王冠、进化石；
- 链上资产的外观（owner、status）是真的，但**资产的价值属性不是链上规则产出的**，后端才是实际裁判。

**修复（建议）**：

- `MintFromCapture`、`RevealAndVerify` 加 `requireRole(ctx, 'system')`；
- `ApplyGrowth` 拆成：
  - `SystemApplyGrowth`（system only，后端在扣费/校验学习表/进化条件后调用）；
  - `SetNickname`（owner only，只改 name）；
  - 或至少在链上校验 `evs` 增量、`ivs` 只增、`level` 与 `exp` 的曲线、`speciesId` 的进化合法性；
- 更彻底的做法：让 `MintFromCapture` 从 `resultHash` 派生 IV/性格/闪光，链上重算，而不是信任入参 `ivsJSON`。

#### C4：真链模式“代码是真的，部署是断的”

这是本次评审最意外的部分。按仓库文档走真链，至少会连续撞上 4 个阻塞：

1. **CA 注册必失败**：`FabricCaService.registerAndEnroll` 显式注册 `hf.EnrollmentID`（`backend/src/fabric/fabric-ca.service.ts:74-77`，HEAD）。Fabric CA 把它当固定属性，返回：
   ```text
   403 Authorization failure: Cannot register fixed value attribute 'hf.EnrollmentID'
   ```
   这会让真链注册接口直接 500，新玩家无法进入游戏。
2. **CA TLS 校验失败**：`.env.example:35`、`docker-compose.yaml:120`、`docs/deployment.md:185/201` 都指向 `network/organizations/fabric-ca/org1/tls-cert.pem`。这是 CA 的**叶子证书**（issuer 是 `ca.org1.pokechain.com`），不是根 CA；Node 的 `fabric-ca-client` 会报：
   ```text
   unable to verify the first certificate
   ```
   正确路径是 `network/organizations/peerOrganizations/org1.pokechain.com/ca/ca.org1.pokechain.com-cert.pem`（自签根）。
3. **system 身份没有自动创建/挂载**：`FabricCaService.ensureSystemIdentity()` 只有定义，全仓库没有调用点（`grep ensureSystemIdentity` 只命中定义）。`docs/deployment.md` §4.4 要求手工 enroll，但根 compose 的 `[real-fabric]` 说明只让取消 volumes/networks 注释，**没有挂载 `backend/.fabric-certs`**；容器里 system 证书不存在，所有 `CreateBattle`/`SubmitResult`/`SettleBattle` 都会失败。
4. **链码安装/运行链路不闭合**：`scripts/deployCC.sh:40` 打的是 `lang=node` 包；`network/config/core.yaml:602-606` 只配置了 ccaas external builder；本机 Docker 29 下 node 包 Docker build 失败（`write unix @->/run/docker.sock: broken pipe`）。当前运行中的网络提交的是 `pokemoncc_review` 外部链码包，但 `172.22.0.1:19999` 没有服务，所有 invoke 都以 `context deadline exceeded` 失败。`deployCC.sh` 的幂等检查只看 version/sequence（`:31-34`），所以它认为“已部署”，不会修复。

我们在评审环境里做了 4 个临时修复后，真链 25/25 通过：

- 删掉 `hf.EnrollmentID` 注册属性；
- CA TLS 指向组织 CA 根证书；
- 按 `docs/deployment.md` §4.4 手工 enroll system 身份；
- 打一个 ccaas 包，升级到 sequence 2，在 `pokechain_net` 内启动链码服务。

**这说明链码本身能跑，Fabric 也是真的；但“按 README/compose 一键真链”目前不成立。** 对一个以“真链”为验收点的课程项目，这是必须在答辩前修掉的。

### 2.1.3 交易与对战的状态机问题

- **C5 交易锁对方资产**：`CreateTrade` 在创建时就对 `offer` 和 `request` 双方资产做 `LOCKED_TRADE`。正常语义应该是“发起人锁自己的 offer，接收方确认时才锁 request”。当前实现导致：
  - 任何用户只要知道对方宝可梦/道具 id，就能创建一笔“请求对方资产”的交易，把对方资产锁住；`ttlSeconds` 只有 `@Min(10)`，没有上限，可以锁很久；
  - 受害者可以 `CancelTrade` 解锁，但攻击者可以反复创建；受害者必须持续处理；
  - 结合 C1，攻击者还可以直接用自己的证书替受害者 `ConfirmTrade`，双方确认后交易执行，**等于零成本拿走对方资产**。
  - 实测：A 创建 `request` 为 B 的 ledyba 的交易后，B 的宝可梦立即 `LOCKED_TRADE`；B 取消后恢复。这说明锁资产路径确实可被第三方触发。
- **C6 Forfeit 不写 winner**：`Forfeit` 调 `settle` 后只写 `status`/`arbiterNote`，不写 `battle.result`。真链账本显示：
  ```json
  {"status":"SETTLED","settledAt":"...","result":{"winnerId":"","resultHash":"","serverSig":"","serverSubmitted":false}}
  ```
  但 A 的积分确实从 1070 → 1110（赢得 20P escrow）。**钱转了，结果没记**。前端结算页、回放、排行榜都读 `result.winnerId`，会显示空赢家。Mock 适配器会写 `winnerId`，所以 367 个测试全绿，真链才暴露。
- **H4 排行榜**：链上 `BattleSettled` 只发 `{id, winnerId}`，不发 `playerA/playerB`；`settle` 也不发 `PointsChanged`。`LeaderboardController` 只读 `payload.playerId/playerA/playerB`，真链下每次对战都不会刷新 ZSET。Mock 发 `playerA/playerB`，所以 Mock 下看起来正常。
- **H5 房间孤儿锁**：`battles.service.ts` 在 `createBattle`/`activateBattle`/`startBattle` 之后才写 `room.battleId`；中间任何一步失败，链上已 `ACTIVE` 且资产锁定，本地房间没有 battleId，`reconcileRoom` 又对 `!room.battleId` 直接 return false → 资产永久冻结，房间不可删/不可对账。

### 2.1.4 后端/前端其它确认问题

- **H1 BOLA**：`GET /pokemon/:id` 无归属校验。实测 B 读取 A 的 spearow，返回完整 `ivs/evs/nature/level`。房间详情又公开对手队伍 id，等于“先侦察再押注”。
- **H2 队伍重复**：`assertTeamSize` 只查长度 1-6，不查重复；实测 `teamPokemonIds` 传 6 个相同 id 返回 201，`teamA` 是 6 个同一只。战斗引擎按槽位构建，等于 6 条命；押注房可用“最强一只 ×6”稳赢。
- **H6 免费学技能**：`learnMove` 只校验 `getMove` 存在，不校验 TM、不校验学习表、不扣费，直接 `applyGrowth({moves})`。
- **H7 锁定资产先消耗**：`items.service` 先 `consumeItem`，再 `applyGrowth`/`applyExp`；`mustOwnPokemon` 不校验 `status=IDLE`。链上第二次调用会 `ASSET_LOCKED`，但第一次消耗已提交，道具/积分被吞。
- **H8 错误码**：`AllExceptionsFilter` 只处理 `HttpException`；链码 `CodedError` 没有 HTTP 状态，统一 500。`train` 积分不足实测返回 500，而文档写 400/409。
- **H9 首球 reveal**：`capture.service.ts:235-241` 和 `wild.service.ts:321-327` 在第一次投球时就 `RevealAndVerify`；`/fairness` 是 `@Public`，返回 `serverSeed`。玩家拿到种子后可计算后续每一次投球成败、IV/性格/闪光，以及野怪 AI 的每个掷点。这违背了“揭示前不可预测”的设计目标；commit-reveal 只保证了“服务器不能换种子”，没有保证“结果不可被玩家挑选”。
- **H10 注册 faucet**：注册送 1000P，且 `TransferPoints`/交易可直接转给主号；登录/注册限流 10/min/IP，脚本可批量。一个 1000P 小号就是一次免费转账。
- **H11 传说钥匙**：`checkLegendaryGate` 只在“已拥有该池传说”时拒绝；钥匙不消耗；击倒传说（不拥有）不算“已拥有”，可以反复进池刷 45-50P/场。5000P 的钥匙约 100-111 场回本，之后是纯收益。
- **H13 大师球**：`shop.data.ts:12` 说“仅作为奖励发放”，但掉落表只有伤药/精灵球/超级球，没有任何任务/排行奖励；`master-ball` 在玩家侧实际不可获得（只有 admin/seed 能发）。金冠 15000P 的边际战力远低于训练（EV 未满时），TM 对多数物种只加 0-6% 威力，导致“月级目标”缺乏吸引力。
- **H14-H17 前端**：交易确认 ID 用错（UUID vs username）；战斗 join 只回 state 不回 turn/deadline；Socket 重连固定旧 token；启动 refresh 无超时。这四条都会造成“功能卡死/判负/无法登录”，不是样式问题。
- **H18 randomUUID**：局域网 HTTP（非 secure context）下 `crypto.randomUUID` 不存在，所有变更请求在请求拦截器里抛错，登录也会失败；`CaptureOverlay` setup 还会让场景停在 pause。
- **H19 签名密钥**：`SERVER_SIGNING_KEY` 默认空，启动生成临时 secp256k1；重启后 `/fairness` 返回新公钥，旧 `serverSig` 无法验证。历史对局的可验证性被破坏。
- **H20 admin**：`contractFor` 把 `admin` 映射到 system 证书；`GrantRole` 要求 `role=admin`，真链必失败（文档已承认）。这意味着真链下“后台授角色”不可用，只能靠预置 CA 属性。

## 2.2 方向二：低耦合、高内聚

### 2.2.1 做得好的地方

- **链码确定性纪律**：禁止 `Date.now`/`Math.random`/网络；时间入参；随机只从 `resultHash` 派生。这是 Fabric execute-order-validate 的正确做法。
- **共享键空间 + `common/state.ts`**：6 个合约直接读写同一键空间，不走 `invokeChaincode`，避免跨合约调用的确定性和权限问题；写者集中（Player/Random/Pokemon/Item 各一个合约写，Trade/Battle 作为编排者跨写），耦合可控。
- **`settle` 单一入口**：所有结算路径（Confirm/Settle/Forfeit/Arbitrate）都走同一个 `settle`，失败整体回滚，没有部分结算。
- **`ChainAdapter` 端口 + 薄 Fabric 适配器**：真实链码调用集中在 `fabric-chain.adapter.ts`（296 行），业务层不直接碰 gateway；`ContractService` 统一注入 `idemKey/nowISO`。
- **纯战斗引擎**：`battle-engine.ts`/`battle-math.ts` 只依赖 game-data，PvP/PvE 共用，5 个纯函数测试文件，可测性最好。
- **前端视觉/地图**：像素风统一、地图数据驱动、素材回退，属于课程项目的加分项。

### 2.2.2 主要耦合/内聚问题

| 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|
| **Mock 与链码两套语义** | `mock-chain.adapter.ts` 1535 行 vs 链码 2274 行；错误码/事件/字段/顺序均有差异 | 367 个后端测试只锁 Mock；真链 bug 无法被测试发现 | 抽 `mock/` 子模块，按链码 `common/` 拆分；加“同一输入对两实现断言同一 code/state”的黄金用例 |
| **事件契约无类型** | 链 `PointsChanged` 用 `balance`，Mock 用 `points`；链 `BattleSettled` 无 playerA/B，Mock 有 | 真链排行榜静默失效 | `ChainEventMap` 判别联合，两个适配器共用类型 |
| **`FabricModule` @Global** | `fabric.module.ts:21`，25 个文件注入，只有 `app.module.ts` import 一次 | 模块图失真，隐藏依赖 | 去 @Global，只导出 `ChainAdapter`/`ContractService` |
| **Wild → Ranked 传递依赖** | `wild.service.ts:14` 为拿 `BondService` import 整个 `RankedModule` | PvE 被匹配/机器人/ELO 拖入 | 抽 `BondModule`（`bond.service.ts`+`bond.ts`） |
| **队伍校验重复** | `battles.service.ts:683-700` 与 `ranked.service.ts:932-956` 近乎逐行重复；`assertTeamSize` 定义在 battles 却被 ranked 跨模块 import | 规则改动两处 | 抽 `pokemon/team-eligibility.ts` 纯函数 |
| **Controller 写业务** | `leaderboard.controller.ts:19-36` 订阅链事件维护 ZSET；`assets.controller.ts:41-43` 写 AuditLog | 难测、难复用 | 抽 `LeaderboardService`/`AuditService` |
| **链码所有权转移三处手写** | `pokemon.contract.ts:145`、`trade.contract.ts:64/77`、`battle.contract.ts:159` | bond 重置/解锁/owner 改写在三处漂移 | 抽 `common/custody.ts::transferPokemonOwnership()` |
| **堆叠不变量分裂** | battle 结算归一（`battle.contract.ts:169-173`）；trade 不归一；`mergeStacks` 端口 0 调用 | 同 typeId 多堆叠 | trade 内复用 `mergeIdleStacks`，或删无用交易 |
| **前后端游戏数据重复** | `frontend/src/stores/zone.ts:63-118` 与 `backend/src/game-data/encounter.data.ts:69-130` 全量重复；`wild-battle.ts:79-99` 复制球倍率/捕捉公式 | 改数值两处 | zone 只保留后端 `/capture/zones`；共享 `packages/contract` 或 OpenAPI 生成类型 |
| **前端类型手抄** | `frontend/src/types.ts` 复制 `chain.types.ts` + DTO | 字段漂移 | 生成类型 |

### 2.2.3 结论

模块级边界是清晰的，**不是“高耦合泥球”**；真正的问题是**双实现（Mock/Fabric）和双权威（后端/链码）造成的内聚破坏**。如果只做课程演示，现有结构可以接受；如果要在答辩中讲“低耦合高内聚”，建议先修：
1) Mock/链码对拍测试；
2) 事件类型；
3) 抽 `BondModule`/`team-eligibility`；
4) 去掉 `@Global`。

## 2.3 方向三：真链部署是否真的用了区块链

### 2.3.1 结论

**代码和链路是真的，不是“假链”。** 证据：

- `FABRIC_MOCK=false` 时 `FabricModule` 选择 `FabricChainAdapter`（`fabric.module.ts:30-36`）；它用 `@hyperledger/fabric-gateway` 连接真实 peer，TLS + X.509 + 用户证书签名（`fabric-gateway.service.ts`）。
- 链码真实部署在 `gamechannel`，Org1+Org2 都 approve/commit；背书策略是通道默认 `MAJORITY`（两组织都须背书）。
- 我们在真实链上完成了注册（CA enroll + `RegisterPlayer`）、捕捉（Commit/Reveal/MintFromCapture）、交易（Create/Confirm/Execute）、开房/押注（CreateBattle/ActivateBattle）、认输结算（Forfeit/Settle），并读到真实账本状态：
  ```json
  {"status":"SETTLED","settledAt":"2026-10-25T07:19:22.003Z",
   "playerA":"smkA...","playerB":"smkB...","escrow":{"pointsA":20,"pointsB":20}}
  ```
  A 积分 1070 → 1110，B 1200 → 1130，wins/losses 也变了；`peer channel getinfo` 高度 31。
- `/fairness` 两条等式在真实链事件上复核通过：
  `sha256(serverSeed) == commitHash`；`sha256(serverSeed|clientSeed|eventId) == resultHash`。

**但“开箱即用的真链模式”不成立。** 默认 `docker compose up` 是 `FABRIC_MOCK=true`；真链需要手工取消注释、手工 enroll system、修 CA 证书路径、修 CA 属性、处理链码安装/服务。我们修了 4 处才跑通。对“答辩验收真链”来说，这 4 处都是硬阻塞。

### 2.3.2 真链与 Mock 的关键差异（本次实测）

| 场景 | Mock | 真链 | 后果 |
|---|---|---|---|
| `Forfeit` 后 `result.winnerId` | 有 | 空 | 真链 e2e 第 10 步失败；UI 显示空赢家 |
| `BattleSettled` payload | 带 playerA/B/points | 只有 id/winnerId | 真链排行榜不刷新 |
| `BattleSettled` 后 escrow | 清零 | 保留 | API 返回的 escrow 两模式不同 |
| 错误码 | `NOT_AUTHORIZED`/`INVALID_BATTLE_STATE`/... | `FORBIDDEN`/`BAD_STATE`/... | 前端/测试按 Mock 码写，真链 500/码不符 |
| 大写 wagerHash | 严格比较拒绝 | `toLowerCase` 后通过 | 两模式行为不同 |
| `ApplyGrowth` species/name 校验 | 无 | 有 | Mock 更宽松 |

这些差异不是“实现风格”，而是**真链 bug 无法被 367 个测试发现**的直接原因。

### 2.3.3 真链部署修复清单（P0）

1. 删掉 `hf.EnrollmentID` 注册属性（CA 自动注入）；`hf.EnrollmentID` 改为链码身份校验的依据。
2. CA TLS 路径改为 `network/organizations/peerOrganizations/org1.pokechain.com/ca/ca.org1.pokechain.com-cert.pem`；`.env.example`/compose/docs 三处同步。
3. 启动时调用 `ensureSystemIdentity()`（幂等），或在 `scripts/up.sh` 里 enroll；根 compose 挂载 `./backend/.fabric-certs:/app/.fabric-certs:ro`（或对应工作目录）。
4. 链码安装：
   - 要么在 `network/config/core.yaml` 去掉 ccaas external builder（恢复默认 Docker build），并固定 Docker 版本；
   - 要么提供 ccaas 服务（`connection.json` + 容器）并在 compose 里启动；
   - `deployCC.sh` 的幂等检查比较 `package_id`，不只 version/sequence。
5. 增加 `scripts/real-chain-smoke.sh`：先 `querycommitted`/`GetPlayer` 检查链码可调用，再跑 e2e；CI 里至少跑一次真链冒烟。

### 2.4.2 faucet/sink 估算（休闲 / 活跃 / 工作室）

假设：单场野怪 55s（休闲）/30s（活跃）/20s（工作室）；收服率 10%/5%/0%；竞技场净收益 30/150/0 P/场；不含交易。

|---|---|---|---|---|---|
| 休闲 | 45 min / ~23 场 | **250-450P** | 0.4 天 | 1.3 天 | ~50 天 |
| 活跃 | 2.5 h / ~143 场 | **~2,650P** | 0 天 | 0.2 天 | ~5.7 天 |
| 工作室 | 8 h / ~1,296 场 | **~28,700P** | 0 天 | 0 天 | ~0.5 天 |

### 2.4.3 反馈回路

**R1（正，主回路）**：击倒/收服 → 等级/积分 → 高级区 → 单场 6→30/50P → 买 EV/球 → 战力↑ → 更高效刷 → 回到起点。  
问题：没有日上限，工作室 8h 可以无限放大；高级区与低级区收益差 5-8 倍，导致“先富更富”。

**R2（正，竞技场）**：rating↑ → 准入 20→400 → 补贴 10→200/胜 → 更快满 EV → 胜率↑。  
问题：补贴由系统增发，不是零和；双开/机器人可把补贴转移到主号；大师场 600P/日 vs 青铜 90P/日，差距过大。

**R3（负，设计意图外）**：羁绊 35 天 +5% → 交易/押注易主重置 30 → 投入归零 → 玩家不敢交易/押注。  
这是“反交易”的负反馈：羁绊本应是长期陪伴奖励，但易主惩罚让资产流动性变差。建议改为保留 50%（`max(30, floor(bond/2))`）或把满羁绊加成提到 10%，让“长期持有”与“交易”之间有取舍而不是恐惧。

**R4（负，新手）**：早期 6P/场 vs 治疗 10P/次 → 余额下降 → 不敢治疗 → 战斗失败 → 更穷。  
建议前 3 天中心治疗免费，或注册积分改为 400 但前 10 场击倒双倍。

### 2.4.4 建议的数值/机制改动（加强正反馈，同时堵套利）

| # | 改动 | Before → After | 目的 | 风险 |
|---|---|---|---|---|
| 1 | 野怪击倒积分日上限 | 无上限 → **300P/日**，单场 ≤30P | 堵工作室，保留休闲收益 | 重度玩家会觉得被削；可用“周上限”替代 |
| 2 | 注册积分 | 1000P 可转 → **400P + 72h 内不可转/不可进积分场** | 堵 alt faucet | 新手起步更紧，需配合免费治疗 |
| 3 | 竞技场补贴 | 50% 入场补贴 → **固定奖池/同段位/当日胜场<3**；机器人场 0 补贴 | 堵双开/刷分 | 排队变慢；可加人机填充 |
| 4 | 传说钥匙 | 永久 → **进入即消耗**；同池击倒后 24h 不可再刷；传说区击倒 0 积分 | 堵无限刷点 | 降低传说区热度；可给“首杀”一次性奖励 |
| 5 | 羁绊易主 | 重置 30 → **保留 50%（max(30, bond/2)）**；满羁绊加成 5% → **10%** | 强化长期陪伴正反馈 | 交易估值变高；需观察是否鼓励倒卖 |
| 6 | PvP 经验 | 0 → **胜者队伍每只 +30**（修 H3）；野怪经验 ×1.5 | 接上“战斗→升级→进化”主循环 | 升级过快；可与 rating 差缩放 |
| 7 | 金冠/TM | 金冠 15000 → **6000**；TM 1500 → **800 且可重复使用** | 让中期目标可达、TM 有决策价值 | 积分 sink 变少；需新增外观/称号 sink |
| 8 | 大师球 | 玩家侧无来源 → **传说图鉴 6/6 或赛季前 10 奖励** | 给收藏/竞技目标 | 稀缺性下降；限 1-2 个/赛季 |

> 建议先做 1/2/3/4/6（堵漏 + 接主循环），观察 1-2 周后再动 5/7/8。数值改动要有埋点：日活、场次、积分分布、交易量、羁绊分布、竞技场胜率。

## 2.5 方向五：区块链的重要性与不可或缺性

### 2.5.1 区块链现在提供了什么（正面）

- **资产所有权与状态机**：宝可梦/道具/积分的 owner、`IDLE/LOCKED_TRADE/LOCKED_BATTLE/RELEASED`、`lockRef`，防止双花/错单解锁。
- **原子结算**：交易双确认、对战 escrow、`settle` 单入口，失败整体回滚，不会“钱扣了资产没到”。
- **可验证随机审计**：Commit 先上链、Reveal 链上重算 `sha256(serverSeed)==commitHash`、消费状态机防重放；`/fairness` 可复核。
- **多组织治理**：Org1 运营 + Org2 仲裁；链码升级需双方 approve；仲裁交易要求 Org2MSP+arbitrator。
- **不可篡改事件**：`BattleSettled`/`PointsChanged`/`ItemMerged` 等事件可做链下索引和审计。

这些是**真实且正面**的。没有链，交易/押注/仲裁就只能靠后端数据库，运营方可以改历史；链给了“第三方可验证”的基础。

### 2.5.2 区块链现在**没有**提供什么（关键）

- **用户身份**：`assertCallerIsPlayer` 只比 MSP；所有玩家在链上等价。链不知道“这是不是小明”。
- **游戏规则裁判**：`MintFromCapture` 信任入参 IV/闪光；`ApplyGrowth` 信任 owner 的 level/EV/IV/species；链不校验成本/学习表/进化条件。
- **对战结果验证**：`SubmitResult` 只检查 `serverSig` 非空，**不验证签名**；`resultHash` 只是后端 turnLog 的哈希，链不重放战斗。后端可以提交任意 winner。
- **私钥主权**：用户私钥由后端托管（课程简化，文档已声明）；后端可以代签任意用户交易。
- **仲裁可用性**：真链下后端只接 Org1 CA，arbiter 没有 Org2 证书；`Arbitrate` 实际只能在 Mock 演示。Org2 的“独立仲裁”在真链上是空的。

### 2.5.3 结论：现在是“必要但不够不可或缺”

**对资产台账/托管/结算/审计：区块链是必要且正向的。**  
**对公平性/规则裁判：区块链目前不是不可或缺的**——把 Fabric 换成一个 PostgreSQL 事务 + 只追加审计表，保留同样的后端逻辑，游戏几乎一样能跑；因为最终裁判权（身份、铸造、养成、对战结果）都在后端。

要让它真正不可或缺，至少要做：

1. **链上身份**：C1 修复，链码能区分“小明”和“小红”；
2. **链上规则**：C2/C3 修复，铸造/养成必须 system + 成本/合法性校验；
3. **结果验证**：`SubmitResult` 验证 `serverSig`（链上存公钥/证书指纹），或把战斗回放哈希/关键掷点上链，允许第三方重放；
4. **仲裁真实化**：真链接入 Org2 CA，端到端跑一次 `Dispute → Arbitrate`；
5. **客户端签名/HSM**：至少提供一条“私钥不出后端”的路径（课程可只做设计+演示）；
6. **真链 CI**：把“真链 25/25”变成每次提交都跑的测试，而不是答辩前手工修。

做到这 6 点，区块链才从“可信数据库”变成“游戏裁判”。

## 6. 最终判断

PokeChain 的**工程完成度高于一般课程作业**：链码/后端/前端/网络/文档都成体系，测试数量可观，真实 Fabric 链路也能跑通。它的问题不是“造假”，而是**权威边界没有守住**：

- 链码把“用户是谁”“能不能铸造”“能不能养成”交给了后端；
- 后端把“真链怎么部署”留给了手工步骤；
- 测试把“链码语义”锁在了 Mock 上。

因此，当前版本的区块链是**可信的资产台账 + 结算/审计层**，但还不是**公平裁判层**。把 C1-C6 修掉、把真链 CI 建起来，这个项目才能真正回答“为什么必须用区块链”，而不是“为什么可以用区块链”。
